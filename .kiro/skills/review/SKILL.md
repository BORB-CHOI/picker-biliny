# 코드 리뷰 (Review)

스태프 엔지니어 관점에서 코드를 리뷰한다. CI는 통과하지만 프로덕션에서 터지는 버그를 찾는다. 명백한 문제는 자동 수정하고, 판단이 필요한 문제는 사용자에게 묻는다.

## 언제 사용하는가

- "코드 리뷰 해줘", "내 diff 확인해줘" 같은 요청이 있을 때
- PR을 올리기 전에 점검하고 싶을 때
- 변경사항의 품질을 확인하고 싶을 때

## 리뷰 프로세스

### 1단계: 변경 범위 파악

```bash
git diff main --stat
git log --oneline -10
```

- 어떤 파일이 변경되었는지 파악
- 변경의 의도와 범위를 이해

### 2단계: 아키텍처 리뷰

- 전체 시스템 설계와 컴포넌트 경계
- 데이터 흐름 — 해피 패스 + 에러 패스
- 커플링 우려 — 이전에 없던 결합이 생겼는가?
- 보안 — 인증 경계, 데이터 접근 패턴

### 3단계: 에러 & 예외 맵

변경된 코드에서 실패할 수 있는 모든 경로를 매핑:

```
메서드/코드패스          | 실패 가능성              | 예외 클래스
------------------------|-------------------------|------------------
ExampleService#call     | API 타임아웃             | TimeoutError
                        | API 429 응답             | RateLimitError
                        | 잘못된 JSON 응답          | JSONParseError
```

- catch-all 에러 처리는 코드 스멜이다. 구체적인 예외를 명시한다.
- 모든 에러는 retry, graceful degradation, 또는 re-raise 중 하나여야 한다.

### 4단계: 코드 품질

- DRY 위반 — 같은 로직이 다른 곳에 있으면 적극적으로 지적
- 네이밍 — 클래스, 메서드, 변수가 하는 일을 이름으로 표현하는가?
- 엣지 케이스 — "X가 nil이면?", "API가 429를 반환하면?" 등 명시적으로 나열
- 과잉 엔지니어링 — 아직 없는 문제를 해결하는 추상화가 있는가?
- 과소 엔지니어링 — 해피 패스만 가정하고 방어 코드가 없는가?

### 5단계: 테스트 리뷰

- 새로운 코드패스마다 테스트가 있는가?
- 해피 패스 테스트 + 실패 패스 테스트 + 엣지 케이스 테스트
- 테스트 피라미드 — 유닛 많이, 통합 적당히, E2E 소수?
- 플레이키 리스크 — 시간, 랜덤, 외부 서비스에 의존하는 테스트?

### 6단계: 성능

- N+1 쿼리
- 메모리 사용량 — 새 데이터 구조의 프로덕션 최대 크기
- DB 인덱스 — 새 쿼리에 인덱스가 있는가?
- 캐싱 기회

### 7단계: 보안

- 입력 검증 — 모든 사용자 입력이 검증, 새니타이즈되는가?
- 인가 — 사용자 A가 사용자 B의 데이터에 접근할 수 있는가?
- 인젝션 — SQL, 커맨드, 템플릿, LLM 프롬프트 인젝션

## 출력 형식

각 발견사항을 분류한다:

- **자동 수정**: 명백한 문제 → 수정하고 보고
- **질문**: 판단이 필요한 문제 → 사용자에게 옵션 제시
- **정보**: 알아두면 좋은 사항 → 간단히 언급

```
코드 리뷰 결과
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[자동 수정] 2건 — 수정 완료
[질문] 1건 — 레이스 컨디션 가능성 → 사용자 확인 필요
[정보] 3건 — 개선 가능 사항
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 핵심 원칙

- 구체적으로. 파일명, 함수명, 라인 번호를 명시한다.
- "이슈가 있다"가 아니라 "auth.ts:47에서 세션 만료 시 undefined를 반환한다"
- 품질에 대해 직설적으로. "잘 설계됨" 또는 "이건 엉망이다."
- 사용자 결과와 연결한다. "이게 중요한 이유는 사용자가 매 페이지 로드마다 3초 스피너를 보게 되기 때문이다."
