# 오피스 아워 (Office Hours)

YC 오피스 아워 스타일의 제품 기획 세션. 코드를 쓰기 전에 문제를 정확히 이해하고, 전제를 검증하고, 대안을 탐색한다.

## 언제 사용하는가

- "이거 만들어볼까?", "아이디어가 있는데", "이거 해볼 만한가?" 같은 질문이 나올 때
- 새 기능이나 제품을 기획할 때
- 코드 작성 전에 방향을 잡고 싶을 때

## 워크플로우

### Phase 1: 맥락 파악

1. 프로젝트 구조와 최근 변경사항을 파악한다
2. 기존 설계 문서가 있으면 읽는다
3. 사용자에게 묻는다: "이걸로 뭘 하고 싶으세요?"

모드 분기:
- 스타트업/사내 프로젝트 → **스타트업 모드** (Phase 2A)
- 해커톤/사이드 프로젝트/학습/오픈소스 → **빌더 모드** (Phase 2B)

### Phase 2A: 스타트업 모드 — 6가지 강제 질문

한 번에 하나씩 질문한다. 각 질문에 구체적이고 증거 기반인 답이 나올 때까지 파고든다.

**Q1: 수요 현실** — "누군가 이게 내일 사라지면 진짜 화낼 거라는 가장 강력한 증거가 뭔가요?"
- "관심 있다"는 수요가 아니다. 행동, 결제, 의존이 수요다.

**Q2: 현재 상태** — "지금 사용자들이 이 문제를 어떻게 해결하고 있나요? 그 비용은?"
- 아무도 아무것도 안 하고 있다면, 문제가 충분히 아프지 않을 가능성이 높다.

**Q3: 구체적 타겟** — "이게 가장 필요한 실제 사람의 이름, 직함, 상황을 말해주세요."
- "헬스케어 기업"은 사람이 아니다. 이메일 보낼 수 있는 구체적인 사람이 필요하다.

**Q4: 가장 좁은 쐐기** — "이번 주에 누군가 돈을 낼 만한 가장 작은 버전은?"
- "플랫폼 전체를 만들어야 쓸 수 있다"는 위험 신호다.

**Q5: 관찰과 놀라움** — "실제로 누군가 이걸 쓰는 걸 옆에서 지켜본 적 있나요? 뭐가 놀라웠나요?"
- 설문은 거짓말한다. 데모는 연극이다. 관찰만이 진실이다.

**Q6: 미래 적합성** — "3년 후 세상이 달라졌을 때, 이 제품은 더 필수적이 되나요, 덜 필수적이 되나요?"
- "시장이 매년 20% 성장"은 비전이 아니다.

### Phase 2B: 빌더 모드 — 디자인 파트너

열정적인 협력자로서 아이디어를 함께 발전시킨다.

1. "이걸 가장 멋지게 만들면 어떤 모습일까요?"
2. "누구한테 보여줄 건가요? 뭘 보면 '와' 할까요?"
3. "실제로 쓸 수 있는 걸 가장 빨리 만드는 방법은?"
4. "비슷한 기존 것 중 가장 가까운 건 뭐고, 어떻게 다른가요?"
5. "시간이 무한하다면 뭘 추가할 건가요? 10배 버전은?"

### Phase 3: 전제 검증

솔루션을 제안하기 전에 전제를 도전한다:
- 이게 맞는 문제인가? 다른 프레이밍이 더 단순하거나 임팩트 있지 않은가?
- 아무것도 안 하면 어떻게 되나? 진짜 아픈 건가, 가설인가?
- 기존 코드 중 이미 부분적으로 해결하는 게 있나?

전제를 명확한 문장으로 정리하고 사용자 확인을 받는다.

### Phase 4: 대안 생성 (필수)

최소 2-3개의 구현 접근법을 제시한다:

```
접근법 A: [이름]
  요약: [1-2문장]
  노력: [S/M/L/XL]
  위험: [낮음/중간/높음]
  장점: [2-3개]
  단점: [2-3개]
  재사용: [기존 코드/패턴]
```

하나는 "최소 실행 가능" (가장 적은 파일, 가장 작은 diff)
하나는 "이상적 아키텍처" (장기적으로 가장 좋은 궤적)

추천과 이유를 제시하고 사용자 승인을 받는다.

### Phase 5: 설계 문서 작성

승인된 접근법으로 설계 문서를 작성한다:

- 문제 정의
- 수요 증거 (스타트업 모드) / 핵심 매력 (빌더 모드)
- 제약 조건
- 검증된 전제
- 검토한 대안들
- 추천 접근법과 근거
- 미해결 질문
- 성공 기준
- 다음 단계

### Phase 6: 핸드오프

설계 문서가 승인되면:
- 다음 스킬 추천: 기획 리뷰(`/plan-ceo-review`), 엔지니어링 리뷰(`/plan-eng-review`), 디자인 리뷰(`/plan-design-review`)

## 핵심 규칙

- 절대 구현하지 않는다. 이 스킬은 설계 문서만 만든다.
- 질문은 한 번에 하나씩.
- 모든 세션은 구체적인 다음 행동으로 끝난다.
- 사용자가 완성된 계획을 가져와도 Phase 3(전제 검증)과 Phase 4(대안)는 반드시 실행한다.
