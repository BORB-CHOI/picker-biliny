# 플랜 (Plan)

코드를 쓰기 전에 체계적인 구현 계획을 세운다. 요구사항을 재정리하고, 리스크를 파악하고, 단계별 실행 계획을 만든다. 사용자 확인 전까지 절대 코드를 작성하지 않는다.

## 언제 사용하는가

- 새 기능을 시작할 때
- 큰 아키텍처 변경이 필요할 때
- 복잡한 리팩토링을 할 때
- 여러 파일/컴포넌트에 걸친 변경이 필요할 때
- 요구사항이 불명확하거나 모호할 때

## 워크플로우

### 1단계: 요구사항 분석

- 요청을 완전히 이해한다
- 필요하면 명확화 질문을 한다
- 성공 기준을 정의한다
- 가정과 제약을 나열한다

### 2단계: 아키텍처 검토

- 기존 코드베이스 구조를 분석한다
- 영향받는 컴포넌트를 식별한다
- 유사한 기존 구현을 검토한다
- 재사용 가능한 패턴을 찾는다

### 3단계: 단계별 분해

각 단계에 포함할 것:
- 명확하고 구체적인 액션
- 파일 경로와 위치
- 단계 간 의존성
- 예상 복잡도
- 잠재적 리스크

### 4단계: 구현 순서

- 의존성 기준으로 우선순위 결정
- 관련 변경 그룹화
- 컨텍스트 전환 최소화
- 점진적 테스트 가능하도록 구성

## 계획 문서 형식

```markdown
# 구현 계획: [기능명]

## 개요
[2-3문장 요약]

## 요구사항
- [요구사항 1]
- [요구사항 2]

## 아키텍처 변경
- [변경 1: 파일 경로와 설명]
- [변경 2: 파일 경로와 설명]

## 구현 단계

### 1단계: [단계명]
1. **[스텝명]** (파일: path/to/file.ts)
   - 액션: 구체적인 작업 내용
   - 이유: 이 단계가 필요한 이유
   - 의존성: 없음 / 스텝 X 필요
   - 리스크: 낮음/중간/높음

### 2단계: [단계명]
...

## 테스트 전략
- 단위 테스트: [테스트할 파일]
- 통합 테스트: [테스트할 플로우]
- E2E 테스트: [테스트할 사용자 여정]

## 리스크 & 대응
- **리스크**: [설명]
  - 대응: [해결 방법]

## 성공 기준
- [ ] 기준 1
- [ ] 기준 2
```

## 핵심 원칙

1. **구체적으로**: 정확한 파일 경로, 함수명, 변수명을 사용한다
2. **엣지 케이스 고려**: 에러 시나리오, null 값, 빈 상태를 생각한다
3. **최소 변경**: 기존 코드 재작성보다 확장을 선호한다
4. **패턴 유지**: 기존 프로젝트 컨벤션을 따른다
5. **테스트 가능하게**: 각 단계가 검증 가능하도록 구성한다
6. **점진적으로**: 각 단계가 독립적으로 확인 가능해야 한다
7. **결정 문서화**: 무엇을 하는지뿐 아니라 왜 하는지 설명한다

## 크기 조절과 단계 분리

기능이 클 때는 독립적으로 배포 가능한 단계로 나눈다:
- **1단계**: 최소 실행 가능 — 가치를 제공하는 가장 작은 조각
- **2단계**: 핵심 경험 — 완전한 해피 패스
- **3단계**: 엣지 케이스 — 에러 처리, 엣지 케이스, 폴리시
- **4단계**: 최적화 — 성능, 모니터링, 분석

각 단계는 독립적으로 머지 가능해야 한다.

## 위험 신호 체크

- 50줄 넘는 함수
- 4단계 넘는 중첩
- 중복 코드
- 에러 처리 누락
- 하드코딩된 값
- 테스트 누락
- 성능 병목
- 테스트 전략 없는 계획
- 파일 경로 없는 단계
- 독립 배포 불가능한 단계

**중요**: 사용자가 "예" 또는 "진행"으로 명시적으로 확인하기 전까지 절대 코드를 작성하지 않는다.
